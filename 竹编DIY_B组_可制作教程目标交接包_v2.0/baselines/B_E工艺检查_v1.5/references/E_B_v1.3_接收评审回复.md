## 请 A / B / D 对齐的接口项

### 1. B 的结果 sourceKey 不能覆盖 D 来源键

B 提案采用 `schemaVersion: 1.3`、`designVersion`、`carrierType`、`customBoundaryHash` 等字段；当前 D 快照仍为 `schemaVersion: 0.3`，含 `designId/designRevision/generatedFromRevision` 和 `patternPlacementKey`。

建议 A 确认：原样保留 D `sourceKey`，另外保存 E 检查器、规则集、证据集版本及自定义上下文摘要。B 的结果版本应与 D 数据版本分别命名，不能直接将 D 的版本号改为 1.3。B 提案未列出的 `patternPlacementKey`、确认结果来源与当前设计版本也不能在适配中丢失。

当前 E 继续使用现有自有结果格式并新增 B 规则／证据版本字段；**尚未替换为 B 的全套结果 JSON Schema**。需要 A 确认字段映射后再输出公共适配器。

### 2. 自定义快照缺少正式检查上下文

当前 D 自定义 v0.2 仅有轮廓、参数、裁切竹条段和交点，没有独立的有效区、先编后裁毛坯、明确的有无手柄声明及区域，也没有与固定扇面等同的完整来源键。其竹条按裁切段编号，不能直接当作 v0.3 的原竹条材料身份。

请 A / D 提出这些字段的正式合同。补齐前，E 可以指出现有几何和结构错误，但相关工艺规则只能 pending；不能把“无数据”当作“无手柄”“无外侧区”或“已经连续”。本次没有自行改动 D 公共接口。

### 3. 规则表需要与机器清单对应

B 的 Markdown 有 `CUSTOM_HANDLE_CONTEXT`、`CUSTOM_EDGE_FINISH_EVIDENCE`、各编法相位与参数依据等细分规则，而机器 JSON 的 17 项清单使用了不同的分组，未逐项列出。请 B 明确别名／父子关系，以及哪些是必检、哪些可 notApplicable。

“重点图案需要完整辨识”还缺少用户重点标记或明确的可执行定义；不能仅将所有着色线段等同于重点图案。该规则需 A / B / C 对齐，当前不臆造自动失败条件。

B 的六种载体范围不代表当前 D 已实现六种快照；当前自动消费仍限于 D 已接入的三种固定扇面。

### 4. 示例与 Schema 目前不足以充当验收证据

示例中的 `sha256:REPLACE_WITH_REAL_HASH`、`D-GEN-v0.3`、summary 的通过计数都是说明性占位，未用于 E 运行结果或通过依据。

建议 B 加强结果 Schema：约束所有输出开关为关闭、计数为非负数，补齐 location/basis 的必填和可空字段，并定义 notApplicable 的记录位置。当前 Schema 并不能阻止输出开关被写成 true，也不能验证 summary 与实际规则记录一致。建议共同确认一份必检覆盖清单，防止未执行的规则被误算为通过。
